现场投屏：完整方案

Open Anywhere · 小智云聊 S3 MAX 固件链路 2026-10-31 方案 · Phase 1–5 完成，固件已上机验证发现与投放

语音说一句，云端生成应用并在 Render 上跑起来，现场的电视出现画面。这条链上谁负责什么，什么叫「设备投屏」， 为什么云端投屏退成调试工具，以及要改哪些文件、怎么验收——本文是完整的一版。

进度（2026-10-31）：Phase 1 控制面、Phase 2 模拟器、Phase 3 固件、Phase 4 文档均已落地；Phase 5 把 SSDP 发现与 DLNA 控制整体搬进固件，设备不再依赖本地 casting。控制面侧在 feat/device-casting 分支（cdc1030，已推到 origin）；固件在 feat/casting-mcp 分支（499e0ba 之后又有未提交的内置发现改造）。模拟器单测全绿，固件在 ESP-IDF v6.1 上编译通过。 本机整链已跑通：create-app → start-app → self.cast.cast → Macast 出画面，语音说完到电视播放「一题双答」，见 10 联调记录。 固件已上机验证：设备自己 SSDP 发现 2 台渲染器，SOAP 投放后 Macast 实际拉流播放，停止返回 200，见 10 联调记录。 还没跑：灵矽下发的真实 tools/list、语音说「投到客厅电视」的整链、真实商用电视。

结论 1
产品只保留一条投屏路径：设备 MCP 自己发现电视、自己发 DLNA
结论 2
Go casting 服务冻结，只作桌面调试与模拟硬件的联调工具
结论 3
设备不出网、不持凭据，身份头只出现在灵矽 → 控制面

01链路：谁负责什么

三个平面各管一段，灵矽在中间编排。设备 MCP 不是「云端 MCP 的客户端」，而是灵矽伸进现场的那只手——灵矽没有别的办法触达现场，只有这条已经建好的设备通道。

1
用户说话小智设备 → 灵矽云，ASR / 意图识别，会话里带 features.mcp
2
灵矽调云端 MCP 建应用create-app 异步返回，语音回合不等待构建
3
灵矽调云端 MCP 启动start-app(app_id) 只启动 Render，返回 stream_url，不碰任何屏幕
4
灵矽调设备 MCP 找屏幕self.cast.list_screens → 固件返回后台 SSDP 扫描缓存的电视列表
5
灵矽把地址交给设备self.cast.cast(url, target_id) → 固件直接向电视发 SOAP
6
电视拉流固件发 DLNA SetAVTransportURI + Play，电视自己向云端 Render 拉 mpegts
关键：三段网络，只有一段是新的
设备 ↔ 灵矽、灵矽 ↔ 控制面都是既有通道；新增的只有设备 ↔ 电视这一段（SSDP 多播 + SOAP），只在局域网里，不出网、不需要隧道，也不需要任何中间服务。

另一条链路：人

浏览器不经过灵矽。Portal 要显示屏幕状态、要能远程停屏，只能靠 Gateway；而 Gateway 在设备投屏模式下够不到现场。

语音：灵矽 → 设备 MCP（SSDP + DLNA）→ 电视　已通
人：浏览器 → Gateway → 现场（无通道）　本方案的已知损失

这一段的补法是让设备固件把自己缓存的屏幕状态通过语音连接上报给控制面，但它属于共享现场多租户场景，不在本期。见 08 风险。

02目标与范围

目标

  • 一条语音回合内完成「生成应用 → 云端启动 → 投到现场电视」。
  • 设备端只做现场的事：发现屏幕、把给定地址投出去。不建应用、不跑 Render、不调云端。
  • 去掉设备上的云端凭据：设备不需要 MCP token，也不需要知道控制面地址。

本期交付

  • 控制面：应用可以存在于「Render 已启动、尚未上屏」的状态，并把 stream_url 返回给灵矽。
  • 小智固件：self.cast.* 改成 3 个工具，并在固件内实现 SSDP 发现与 DLNA 控制（不再依赖本地 casting 服务）。
  • 模拟器 voiceentry：与设备同构的 device 实现，无硬件时跑通整条链。
  • 文档：作废「现场隧道」，重写现场边界与固件说明。

不包含

  • 反向隧道（语音链路不需要；Portal 需要时另行决定）。
  • 控制面 screen 模块的下线——它继续服务云端投屏这条调试路径。
  • 会话内换源、AirPlay、多屏并发、计费。

03规则与边界

  1. 投屏路径上设备只访问现场局域网。发现与控制都是设备 → 电视，不经过云端；X-Linx-* 三个身份头只出现在灵矽 → 控制面这一段，由平台自动注入。
  2. 媒体地址由云端给出，电视自己拉流。Render 的 -public-url 必须公网可达，按每屏 2–8 Mbps 预留上行。
  3. 一屏一会话由电视自己的 UPnP 状态保证。控制面不参与占用仲裁，也不实现 force；设备只记录最近一次投屏，重复 cast 直接覆盖。
  4. 语音回合不等待构建。create-app 异步返回；start-app 在 Render 就绪后作为另一次独立调用发生。
  5. playing 不等于出画。它只代表设备确认了播放指令，验收必须看电视实际画面。
  6. 设备端投屏不监听端口。链路纯出站；SSDP 与 SOAP 都只在可信局域网内，设备与电视必须同广播域。
  7. 云端投屏不可作为产品能力出现。不出现在 Portal、不进部署文档，只由开发配置开启。

05设计：控制面

5.1 start-app 的产品语义

产品路径上它只做一件事：把已构建完成的应用在 Render 上启动，返回流地址。

start-app(app_id)              → { app_id, state: "running", stream_url, ... }
stop-app(app_id)               → 停 Render，电视由设备工具停

不再接受 screen_id：屏幕不在云端视野里，传进来也没人能执行。原来那段建 casting 会话的代码（service.go:1270-1304）保留在仓库里，但产品不再有任何入口触发它；调试时直接对 casting 发 HTTP，见 13。

5.2 返回流地址

StatusView 增加 stream_url，在 state == running 且 Source.URL 非空时填充。地址就是 Render 已经生成的那个，不做拼接、不转码。

5.3 状态机风险（已核对）

running 现在允许「没有屏幕」——已逐条验证

app.State 仍是 building / idle / running / error，但 running 不再隐含已上屏，取值允许 ScreenID == ""。担心的是清理和重启恢复会把它当成异常，实际核对结果：

  • OccupiesScreen()（app/app.go:131）先判 ScreenID != ""，无屏 running 返回 false ✓
  • checkRunning：只看进程与流，没有投屏会话不会报错，也不会发通知 ✓
  • StopApp：只删 Render 实例，不调 casting ✓
  • removable / hasActiveResources：running 仍算活跃资源，不会被 prune 误删 ✓
  • Portal 应用详情：screen_id 为空时按无屏展示，不崩 ✓

结论：状态机不需要新增状态，也不需要迁移；running 的语义从「在屏幕上跑」收窄为「云端在跑、流可用」。

5.4 兼容

  • 云端投屏路径的代码与测试全部保留，只是不再被产品调用。
  • 存量部署在切换前不能断：切换顺序是先确认部署形态（一现场一 owner），再关掉云端调用。

06设计：设备 MCP

固件里的 main/casting/ 不删，继续改写：目标从「本地 casting HTTP」再进一步，改成设备自己实现 SSDP 发现与 DLNA 控制。删掉 cast_client.*、身份头、token、JSON-RPC 封装、构建轮询与主动播报，现场不再需要任何服务。

6.1 工具面

工具参数行为
self.cast.list_screens—读后台缓存的电视列表，对模型报「名字 + 状态」（Macast(...)空闲）；稳态下不访问网络，首次调用且从未扫成功时同步扫一次
self.cast.casturl, target_id按 id → 唯一名字解析目标，缓存没命中就现场扫一次；然后直接向电视的 controlURL 发 SetAVTransportURI + Play
self.cast.stopsession_id（可选）发 Stop；不传时停本设备最近一次投屏，701 视为已停

删掉的 8 个旧工具里，create_and_cast / update_app / app_status / app_operations / app_request / list_apps 全部属于云端，灵矽直接调云端 MCP 即可。

6.2 发现与缓存

  • 新增 main/casting/ssdp.*：M-SEARCH 到 239.255.255.250:1900，2.5 秒窗口收单播应答，按 Location 去重。
  • 新增 main/casting/dlna_renderer.*：拉 description.xml（32 KB 上限），找 MediaRenderer + AVTransport，解析 controlURL；SOAP 带 DIDL-Lite 元数据，URL 双重转义。
  • 新增 main/casting/xml_lite.*：事件式 XML 解析，深度 16、输入 32 KB，只服务描述与 SOAP Fault。
  • 后台任务每 CONFIG_CASTING_SCAN_INTERVAL_SEC（默认 60 秒）扫描一次；结果缓存最多 16 台，连续 3 次没看到或 max-age 过期标离线，连续 6 次才删除（正在投屏的那台保留）。

6.3 配置

  • 新增单一配置 CONFIG_CASTING_SCAN_INTERVAL_SEC（int，默认 60，范围 10–600）。
  • 删除 CONFIG_CASTING_URL 与 NVS casting/url；不再有服务地址可配。
  • 删除 CAST_MCP_URL、CAST_MCP_TOKEN、CAST_AGENT_ID、CAST_DEVICE_ID。

6.4 不做的事

  • 不轮询构建：等待回到灵矽侧，用户再问一次或灵矽自己查 get-app-status。
  • 不做主动播报：SendProactiveAnnouncement 与 agent_id_ 的改动一并回退。
  • 不在设备上做会话表：只记录最近一次投屏；换屏时在新屏接受流后停止旧屏，多屏并发与占用仲裁留给后续。
  • 不监听端口、不做 UPnP 事件订阅；Play 返回 200 即视为成功。

真机：转义与停止带参数的 URL 在 CurrentURI 与 DIDL 元数据里分别做一次和两次 XML 转义，假电视按原 URL 收到请求（查询串逐字节一致）；20 秒后 Stop 返回 200
真机：换屏投到假电视后改投 Macast：假电视在 Macast 接受流的同时收到 Stop，Macast 开始拉流；随后 self.cast.stop 返回「已经停止投屏」，Macast 回空闲。旧屏不会留在后台继续播放

本机的 casting 与 Macast 都在这台 Windows 上，所以早期测试流走 loopback；/v1/targets 发现必须用 -interface Meta（默认路由是 VPN 网卡）。固件内置发现后不再有这段限制：设备用 WLAN 地址直接发多播。真机已验证发现、投放与停止，但灵矽下发的真实 tools/list、语音整链和真实商用电视仍未验证。部署上记住：render 的 -public-url 决定电视从哪里拉流，必须是电视可达的地址；-app-host 决定控制面怎么调应用接口，别跟着公网地址走。
