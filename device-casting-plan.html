Open Anywhere · 小智云聊 S3 MAX 固件链路 2026-10-31 方案 · Phase 1–4 完成，待整链联调

语音说一句，云端生成应用并在 Render 上跑起来，现场的电视出现画面。这条链上谁负责什么，什么叫「设备投屏」， 为什么云端投屏退成调试工具，以及要改哪些文件、怎么验收——本文是完整的一版。

01链路：谁负责什么

三个平面各管一段，灵矽在中间编排。设备 MCP 不是「云端 MCP 的客户端」，而是灵矽伸进现场的那只手——灵矽没有别的办法触达现场，只有这条已经建好的设备通道。

1
用户说话小智设备 → 灵矽云，ASR / 意图识别，会话里带 features.mcp
2
灵矽调云端 MCP 建应用create-app 异步返回，语音回合不等待构建
3
灵矽调云端 MCP 启动start-app(app_id) 只启动 Render，返回 stream_url，不碰任何屏幕
4
灵矽调设备 MCP 找屏幕self.cast.list_screens → 固件经局域网问本地 casting GET /v1/targets
5
灵矽把地址交给设备self.cast.cast(url, target_id) → 固件 POST /v1/projection-sessions
6
电视拉流本地 casting 发 DLNA SetAVTransportURI + Play，电视自己向云端 Render 拉 mpegts
关键：三段网络，只有两段是新的
设备 ↔ 灵矽、灵矽 ↔ 控制面都是既有通道；新增的只有设备 ↔ 本地 casting 这一段，而且只在局域网里，不出网、不需要隧道。

另一条链路：人

浏览器不经过灵矽。Portal 要显示屏幕状态、要能远程停屏，只能靠 Gateway；而 Gateway 在设备投屏模式下够不到现场。

语音：灵矽 → 设备 MCP → casting → 电视　已通
人：浏览器 → Gateway → 现场（无通道）　本方案的已知损失

这一段的补法是「现场代理出站上报」（casting 所在的那台机器每 30 秒推一次状态），但它属于共享现场多租户场景，不在本期。见 08 风险。

02目标与范围

目标

  • 一条语音回合内完成「生成应用 → 云端启动 → 投到现场电视」。
  • 设备端只做现场的事：发现屏幕、把给定地址投出去。不建应用、不跑 Render、不调云端。
  • 去掉设备上的云端凭据：设备不需要 MCP token，也不需要知道控制面地址。

本期交付

  • 控制面：应用可以存在于「Render 已启动、尚未上屏」的状态，并把 stream_url 返回给灵矽。
  • 小智固件：self.cast.* 从「代理云端 MCP」改成「直连本地 casting HTTP」，工具面收到 3 个。
  • 模拟器 voiceentry：与设备同构的 device 实现，无硬件时跑通整条链。
  • 文档：作废「现场隧道」，重写现场边界与固件说明。

不包含

  • 反向隧道（语音链路不需要；Portal 需要时另行决定）。
  • 控制面 screen 模块的下线——它继续服务云端投屏这条调试路径。
  • 会话内换源、AirPlay、多屏并发、计费。

03规则与边界

  1. 设备只访问现场局域网。不持 token、不调云端；X-Linx-* 三个身份头只出现在灵矽 → 控制面这一段，由平台自动注入。
  2. 媒体地址由云端给出，电视自己拉流。Render 的 -public-url 必须公网可达，按每屏 2–8 Mbps 预留上行。
  3. 一屏一会话由本地 casting 的 409 保证。控制面不再参与占用仲裁，也不再实现 force 的接管逻辑。
  4. 语音回合不等待构建。create-app 异步返回；start-app 在 Render 就绪后作为另一次独立调用发生。
  5. playing 不等于出画。它只代表设备确认了播放指令，验收必须看电视实际画面。
  6. 现场 casting 无鉴权，只能跑在可信局域网，不得映射公网。
  7. 云端投屏不可作为产品能力出现。不出现在 Portal、不进部署文档，只由开发配置开启。

05设计：控制面

5.1 start-app 的产品语义

产品路径上它只做一件事：把已构建完成的应用在 Render 上启动，返回流地址。

start-app(app_id)              → { app_id, state: "running", stream_url, ... }
stop-app(app_id)               → 停 Render，电视由设备工具停

不再接受 screen_id：屏幕不在云端视野里，传进来也没人能执行。原来那段建 casting 会话的代码（service.go:1270-1304）保留在仓库里，但产品不再有任何入口触发它；调试时直接对 casting 发 HTTP，见 13。

5.2 返回流地址

StatusView 增加 stream_url，在 state == running 且 Source.URL 非空时填充。地址就是 Render 已经生成的那个，不做拼接、不转码。

5.3 状态机风险（已核对）

running 现在允许「没有屏幕」——已逐条验证

app.State 仍是 building / idle / running / error，但 running 不再隐含已上屏，取值允许 ScreenID == ""。担心的是清理和重启恢复会把它当成异常，实际核对结果：

  • OccupiesScreen()（app/app.go:131）先判 ScreenID != ""，无屏 running 返回 false ✓
  • checkRunning：只看进程与流，没有投屏会话不会报错，也不会发通知 ✓
  • StopApp：只删 Render 实例，不调 casting ✓
  • removable / hasActiveResources：running 仍算活跃资源，不会被 prune 误删 ✓
  • Portal 应用详情：screen_id 为空时按无屏展示，不崩 ✓

结论：状态机不需要新增状态，也不需要迁移；running 的语义从「在屏幕上跑」收窄为「云端在跑、流可用」。

5.4 兼容

  • 云端投屏路径的代码与测试全部保留，只是不再被产品调用。
  • 存量部署在切换前不能断：切换顺序是先确认部署形态（一现场一 owner），再关掉云端调用。

06设计：设备 MCP

固件里的 main/casting/ 不删，改写。目标从「云端 /mcp」换成「本地 casting HTTP」，删掉身份头、token、JSON-RPC 封装、构建轮询与主动播报。

6.1 工具面

工具参数行为
self.cast.list_screens—GET /v1/targets，对模型报「名字 + 状态」（Macast(...)空闲）；id 与 endpoint_id 留在设备缓存里
self.cast.casturl, target_id按 id → 唯一名字 → GET /v1/targets/{id} 的顺序解析屏幕，再 POST /v1/projection-sessions，固定 mpegts / h264 / aac；被占用返回 409 原文

删掉的 8 个旧工具里，create_and_cast / update_app / app_status / app_operations / app_request / list_apps 全部属于云端，灵矽直接调云端 MCP 即可。

6.2 配置

  • 新增单一配置 CONFIG_CASTING_URL，例：http://192.168.1.20:8091。
  • 运行时可用 NVS casting/url 覆盖。
  • 删除 CAST_MCP_URL、CAST_MCP_TOKEN、CAST_AGENT_ID、CAST_DEVICE_ID。

6.3 不做的事

  • 不轮询构建：等待回到灵矽侧，用户再问一次或灵矽自己查 get-app-status。
  • 不做主动播报：SendProactiveAnnouncement 与 agent_id_ 的改动一并回退。
  • 缓存最近一次 list_screens 的结果，把模型听到的名字（或 id）解析成 target id 与可用的 endpoint_id；名字撞车时让模型重新确认，缓存里都没有才 GET /v1/targets/{id}。
