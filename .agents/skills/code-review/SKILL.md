# 代码评审（code-review）

`max 档 → 5+5 个角度 × 8 条候选 → 单票验证 → 补漏扫描 → 至多 15 条发现`

你正在以 **max** 档做**召回优先**的评审：抓住每一个真实缺陷。在这一档，抓住真实缺陷比避免误报更重要——漏掉的缺陷会随代码发布。宁可多报。

## 阶段 0 —— 收集 diff

运行 `git diff @{upstream}...HEAD`（没有 upstream 就用 `git diff main...HEAD` / `git diff HEAD~1`），取得待评审的统一 diff。如果有未提交改动，或区间 diff 为空，再运行 `git diff HEAD`，把工作区改动一并纳入范围——评审常常发生在提交之前。如果参数传入了 PR 编号、分支名或文件路径，则改评审该目标。以此 diff 作为评审范围。

## 阶段 1 —— 查找候选（5 个正确性角度 + 3 个清理角度 + 1 个改动层次角度 + 1 个约定角度，每个至多 8 条）

通过 Agent 工具运行 **10 个彼此独立的查找角度**。每个角度给出**至多 8 条候选发现**。不要让一个角度的结论压制另一个——如果两个角度以不同理由指向同一行，两条都记录。如果当前工具集没有 Agent 工具，不要报错——由你在当前上下文中依次完成每个角度（以及每次验证）。

### 角度 A —— 逐行扫描 diff

逐行读完 diff 的每个 hunk，然后 Read 每个 hunk 所在的完整函数——被改动函数中未改动的行也在范围内（本 PR 让它们重新暴露，或没能修好它们）。对每一行追问：什么样的输入、状态、时序或平台会让这一行出错？留意条件写反、差一错误、空指针/undefined 解引用、漏写 `await`、把 0 当假值、复制粘贴时用错变量、catch 里吞掉错误、正则元字符未转义。

### 角度 B —— 删除行为审计

对 diff 中**删除**或替换的每一行，说出它原本守住的约束或行为，再在新代码里找出这个约束在哪里被重新建立。找不到，就是一条候选：被拿掉的守卫、被丢掉的错误路径、被收窄的校验、被删除但确实覆盖了真实场景的测试。

### 角度 C —— 跨文件追踪

对 diff 改动的每个函数，用 Grep 找出它的调用方，检查改动是否破坏了任何调用点：新增的前置条件、变化的返回结构、新抛出的异常、时序或顺序依赖。也要检查被调用方：同一 PR 中的另一处改动，会不会让这个调用变得不安全？

### 角度 D —— 语言陷阱专家

扫描 diff 所用语言/框架的经典陷阱，例如：JS 把 0 当假值、`==` 隐式转换、闭包捕获循环变量；Python 可变默认参数、延迟绑定闭包；Go 向 nil map 写入、range 变量捕获；SQL 注入；时区/DST 漂移；浮点相等比较。凡是 diff 新引入的实例都要标记。

### 角度 E —— 包装器/代理正确性

当 PR 新增或修改了一个包装其他对象的类型（缓存、代理、装饰器、适配器）时：检查每个方法是否都路由到被包装的实例，而不是绕回注册表/会话/全局——例如一个带 `delegate` 字段的缓存 provider，如果通过 `session.get(...)` 而不是 `delegate.get(...)` 解析 ID，就会重新进入缓存或递归。还要检查包装器是否转发了调用方实际用到的全部方法。

### 复用（Reuse）

上面的角度找 bug；这一条和接下来的两条找改动代码里的清理项。标记那些重复实现了仓库已有能力的新代码——用 Grep 搜索共享/工具模块以及改动附近的文件，并点名应改用的既有辅助函数。

### 简化（Simplification）

标记 diff 新增的多余复杂度：冗余或可推导的状态、只差一点的复制粘贴、过深的嵌套、遗留的死代码。给出能做同样事情的更简单写法。

### 效率（Efficiency）

标记 diff 引入的无用功：重复计算或重复 I/O、本可并行的独立操作却串行执行、给启动路径或热路径新增的阻塞工作。也要标记由闭包或捕获环境构造的长生命周期对象——它们在整个对象生命周期内都持有外围作用域（作用域里有大对象时就是内存泄漏）；优先使用只复制所需字段的 class/struct。给出开销更低的替代方案。

### 改动层次（Altitude）

检查每处改动是否在正确的深度上解决根因，而不是用脆弱的补丁掩盖症状。在共享基础设施上层层叠加特例，通常说明修得不够深——相比增加特例，优先对底层机制做更简单、更通用的改动，并点名那处改动。

### 约定（CLAUDE.md）

找出管辖被改动代码的 CLAUDE.md：用户级 `~/.claude/CLAUDE.md`、仓库根目录的 `CLAUDE.md`，以及位于被改动文件任一祖先目录中的 `CLAUDE.md` 或 `CLAUDE.local.md`（某个目录的 CLAUDE.md 只作用于该目录及其下的文件）。把存在的每一份都读一遍，再检查 diff 是否有明确违反其中规则之处。

只有能同时引用**规则原文**和**违反它的代码行**时才标记——不要凭风格偏好，也不要凭“文档精神”这种模糊推断。发现里要写出 CLAUDE.md 路径并引用规则，供报告引用。如果没有适用的 CLAUDE.md，这个角度返回空。

清理、改动层次与约定类的候选使用同样的 `file`/`line`/`summary` 结构；在 `failure_scenario` 中说明具体代价（重复了什么、浪费了什么、维护上更难在哪里，或违反了哪条 CLAUDE.md 规则），而不是崩溃场景。当输出条数触顶需要取舍时，正确性缺陷永远优先于清理、改动层次与约定类发现。

## 阶段 2 —— 验证（单票、三态）

把指向同一行/同一机制的候选去重，保留失败场景最具体的那条。对剩下的每条候选，通过 Agent 工具跑**一个验证者**：把 diff、相关文件和候选交给它，让它只返回下列三者之一：

- **CONFIRMED（已确认）** —— 能说出触发它的输入/状态，以及错误输出或崩溃。引用对应代码行。
- **PLAUSIBLE（有可能）** —— 机制真实存在，但触发条件不确定（时序、环境、配置）。说明什么情况能确认它。
- **REFUTED（已推翻）** —— 事实不成立（代码并非如此），或在别处已有防护。引用能证明这一点的代码行。

保留投票为 CONFIRMED 或 PLAUSIBLE 的候选。

这是召回模式——只要有一票不是 REFUTED，就保留这条发现。不要因为不确定而丢弃。

## 阶段 3 —— 补漏扫描

拿已经验证过的清单，**再跑一个查找者**，以全新评审者的身份重读 diff 和所在函数，**只找**清单里没有的缺陷。不要重新推导或重新确认已有条目——这一轮的任务是补漏。重点关注第一轮容易漏掉的东西：移动/抽取后的代码丢了守卫或锚点；二线陷阱（dataclass 默认值只求值一次、`hash()` 不确定、锁的范围被缩小、带副作用的谓词方法）；测试中 setup/teardown 不对称；配置默认值被翻转。

给出**至多 8 条新增候选**，每条都要点名清单上没有的缺陷。如果没有新东西，就返回空扫描——不要凑数。

## 输出

调用一次 ReportFindings 工具，以 `{level, findings}` 汇报本次评审结果。`findings` 至多 15 条，按严重程度从高到低排列；每条包含 `file`、`line`、`summary`、`short_summary`——把结论压缩到 ≤60 个字符，不写理由或后果从句——`failure_scenario`，以及 `category`——产生该发现的角度的 kebab-case 短标识（`correctness`、`simplification`、`efficiency`、`reuse`、`altitude`、`conventions`，或更贴切的专有标识，如 `test-coverage`）——如果跑过验证，再加 `verdict`。如果存活超过 15 条，保留最严重的 15 条。如果没有任何一条通过验证，就用空数组调用。不要另外把发现当作文本打印，也不要为这次评审创建或发布 artifact——工具调用本身就是报告。

## 如果发现随后被修复

当已报告的发现之后在本会话中被修复时——用户要求你修，或后续工作顺带修好了——你**必须**再次调用 ReportFindings，带上同一批发现，并为每条加上 `outcome`：`fixed`（已修复）、`no_change_needed`（该发现是错的或已被处理）、`skipped`（问题真实但未应用修改）。不要再用文本重复这些发现。

修复落地后立刻调用，先于任何文字总结；宿主界面的逐条状态只认这次调用，不调用的话这些发现会一直显示为未解决。
