# Open Anywhere 商业策略

> 状态：Proposal（供讨论）
> 版本：v0.1
> 日期：2026-10-25
>
> 本文描述商业定位、收入结构与变现载体，供产品讨论与对外沟通使用。文中形态是方向判断，不代表相关能力均已实现；当前能力以代码和演示验证为准。

## 1. 摘要

**Open Anywhere 卖的不是应用，而是“智能体出现在身边任何一块屏幕上”的能力。**

这个判断由三件事支撑：

- **入口是语音。** 说话的交互成本最低，用户不需要寻找工具、安装应用、学习操作。
- **内容是现场生成的。** 应用不为所有人的所有明天准备，只为此刻这几个人、这场活动、这个场合准备。
- **出口是屏幕。** 而屏幕已经存在于每个家庭和每个营业场所里，不需要用户再买一块。

普通聊天、百科问答只是这个智能体的底座能力。真正的主打是：**它能出现在你生活的方方面面，出现在任何一个屏幕上。**

变现发生在 Render 这一端：它是唯一物理落地在现场的组件，既是软件，也是能装箱的硬件，还是天然的计费闸门。

## 2. 定位：不是陪伴机器人

市面上已有一类产品叫陪伴机器人。Open Anywhere 与它们的差别不在能力多少，而在形态：

| 维度 | 陪伴型机器人 | Open Anywhere |
| --- | --- | --- |
| 形态 | 一台专用设备 | 一块已有的屏幕 |
| 场景 | 固定在聊天、陪伴、早教 | 随现场变化：聚会、家庭、课堂、会议、门店 |
| 内容 | 厂商预置，靠内容库扩展 | 现场描述，当场生成 |
| 与人的关系 | 你需要去找它 | 它出现在你正在做的事情里 |
| 扩展方式 | 增加技能和内容 | 增加屏幕，不增加硬件 |

陪伴机器人是“你要去使用的一台设备”。Open Anywhere 是“随时出现在你身边的智能体”——它没有固定的形态，因为它借用现场已经有的那块屏幕。

这条定位带来两个直接结论：

- **获客成本低。** 不需要说服用户买一台新设备，只需要他的房间里有电视。
- **场景没有边界。** 每多一个现场需求，就多一个使用理由，而不是多一份需要预先采购的内容。

## 3. 三层能力：对话、应用、角色

同一个智能体，由浅入深提供三层能力：

| 层 | 用户获得什么 | 例子 |
| --- | --- | --- |
| 对话层 | 聊天、百科、问答，纯语音即可 | 在客厅里随口问一句 |
| 应用层 | 为此刻现场生成的可运行应用，画面共享 | 聚会游戏、讨论看板、做饭计时板 |
| 角色层 | 智能体自己的形象出现在屏幕上，说话时会动 | 电视上出现它的脸，语气和动作跟着对话走 |

三层是递进关系：对话层是入口，应用层是差异化，角色层建立情感连接。

**应用层是商业差异化的核心**——它把“回答一个问题”扩展成“组织一场活动”，价值密度高得多。

**角色层是另一条独立的产品线**，见下一节。

## 4. 角色上屏：一个单独的应用 case

把智能体自己的形象放到电视上，聊天时它会有表情、会动——这是一个独立的应用案例，值得单独设计，而不是当作聊天的可选皮肤。

它成立的理由：

- **功能没变，性质变了。** 只有声音时它是助手，有了形象它就是角色。同一句话，由一个会看向你、会点头的形象说出来，感受完全不同。
- **屏幕的角色被反转。** 在此之前屏幕是输出设备，展示题目和比分；在这里屏幕是智能体的脸。
- **它直接对标陪伴机器人，但不卖硬件。** 竞品需要用户买一台机器放在桌上，我们直接用客厅已有的那块电视。
- **它最容易成为默认状态。** 没有应用在运行时，屏幕上放什么？放它自己——比空屏或等待提示更有价值，也回答了“服务开着但还没生成应用时屏幕应该显示什么”这个问题。

需要验证的问题：

- 形象是否让人更愿意持续对话，还是只在第一次新鲜。
- 动作是否帮助理解（说话时动）还是构成干扰。
- 不同屏幕尺寸和观看距离下，形象应该多大、放在哪、如何取景。
- 它和应用层如何切换：正在玩游戏时，智能体退到角落还是隐藏。

这个 case 的价值不在于功能复杂度，而在于它决定了产品被感知成“工具”还是“角色”。

## 5. 商业模式：三条收入线

同一个内核，三种交付形态，覆盖支付能力和采购习惯完全不同的客户：

| 形态 | 商业角色 | 收入结构 | 解决的问题 |
| --- | --- | --- | --- |
| **云端 Render** | 订阅与按量 | 持续收入、高毛利、零门槛 | 不愿买设备、只想开箱即用的客户 |
| **Render 盒子** | 硬件销售 | 一次性硬件收入 + 渠道铺货 + 后续订阅 | 买设备这一采购习惯；占领客厅入口 |
| **Docker 方案** | 私有化交付 | 高客单年费、边际成本极低 | 大 B 与集成商：可控、可审计、数据不出门 |

三点需要说明：

- **三条线不是三选一。** 它们是同一份技术的价格分层：少一条就漏掉一类客户。只做云端，放弃愿意一次性付费买设备的人；只做盒子，吃不到大 B 的年费。
- **云端与现场节点互补，不互斥。** 投屏必须发生在局域网内，因此云端形态大概率需要一个现场的薄节点来接住——那个节点就是盒子或一台跑 Docker 的机器。更现实的结构是“云做大脑，现场做呈现”。
- **盒子与 Docker 共用同一个 Render 内核。** 差别在授权、分发和运维，不在核心代码。

## 6. 客户分层

| 客户 | 特征 | 主要形态 | 付费方式 |
| --- | --- | --- | --- |
| 个人家庭 | 有电视，不愿部署，需求零散 | 盒子，或云端账号 + 已有设备 | 硬件 + 订阅 |
| 小商家（民宿、轰趴馆、餐厅、门店） | 有屏幕，以营业场景使用 | 盒子，或云端账号 | 硬件 + 月费，或按场次 |
| 大 B 与集成商（酒店、教育、零售） | 要求私有化、可审计、数据不出门 | Docker + license | 年费 license，按节点授权 |

进入顺序建议从能最快验证付费意愿的一层开始，而不是从技术上最容易的一层开始。产品故事中的首个场景（朋友聚会）对应个人与家庭，首个商业验证（民宿、轰趴馆）对应小商家。

## 7. 计费口径

收什么钱，决定了计量点埋在哪里：

| 口径 | 含义 | 适合的客户 |
| --- | --- | --- |
| 屏幕数 | 同时在线几块屏幕 | 家庭与商家订阅 |
| 会话数或运行时长 | 投屏与运行的时长 | 云端按量 |
| 应用创建与修改次数 | 生成了多少个应用 | 高频个人用户 |
| 节点 license | 部署了几个 Render 节点 | 私有化客户 |

**Render 是天然的计量位置。** 每一次投屏会话、每一路视频流、每一块在线屏幕都必须经过它。计量的物理位置就在那里，收费点也在那里——这是选择由 Render 承载商业化的根本原因。

## 8. 为什么是 Render 端

在整条链路里，Render 是唯一同时满足以下条件的组件：

- **唯一物理落地在现场的组件。** 语音入口是别人的硬件，构建在云端，控制面是内部编排，只有 Render 既在现场又属于我们。
- **唯一可以装箱卖的东西。** 软件可以装进盒子，盒子可以铺渠道。
- **计费闸门。** 见上一节。
- **分发通道。** 每块接入的屏幕都是一个入口，装得越多，应用场景触达越广。
- **数据回路。** 应用在什么现场、被如何使用，只有 Render 看得见。

## 9. 验证路径

策略先于实现。三条收入线都需要 Render 具备节点身份、授权校验、远程升级和计量能力；这些在实现阶段展开，不在本文详述。需要按顺序验证的是付费意愿，而不是技术完备度。

| 阶段 | 要验证的问题 | 交付形态 |
| --- | --- | --- |
| 演示与共创 | 用户是否愿意等待构建，定制是否带来明显差别 | 自建 Render |
| 单场试点 | 场地方是否愿意为一场活动付费 | 自建 Render + 云端账号 |
| 小批量盒子 | 商家是否接受一次性硬件采购 | 盒子 |
| 私有化 POC | 大 B 是否接受年费与节点授权 | Docker + license |
| 规模运营 | 计量、续费与支持成本是否可控 | 三条线并行 |

## 10. 本文不做的事

- 不定义授权、计费、节点注册的实现方案，这些属于后续技术设计。
- 不预设三条收入线都能成立。它们是并行假设，各自需要独立的付费证据。
- 不改变当前架构的非目标。当前版本仍是单租户、无计费的演示系统，商业能力的引入需要另立设计并修订架构文档。
