# Open Anywhere 商业策略

> 状态：Proposal（供讨论）
> 版本：v0.2
> 日期：2026-10-25
>
> 本文描述产品定位、收费模式与变现载体，供产品讨论与对外沟通使用。文中的价格与规则是初始假设，会随真实数据调整；相关能力不代表均已实现，当前能力以代码和演示验证为准。

## 1. 摘要

**先说清楚这是什么：一个语音陪伴的智能体。它最重要的特点不是陪聊，而是千人千面的应用。**

同一个玩具——

- 在客厅，它是一场三人知识竞赛；
- 在孩子房间，它是一场亲子问答；
- 在厨房，它是一个分步做饭计时板；
- 在门店，它是一场顾客互动活动。

用户说出来，应用当场长出来，然后出现在身边那块屏幕上。它会聊天、会答百科，但这些是底座能力，不是卖点。**卖点是“千人千面”：同一个玩具，在不同的人、不同的现场，长出完全不同的应用。**

收费从小玩具开始，向三个方向延伸：

| 卖什么 | 怎么收 |
| --- | --- |
| **玩具本身** | 一次性硬件 |
| **应用能力** | 百变积分：包月或充值 |
| **运行能力** | 云端运行时长，或买断运行盒子 |
| **社区版** | 免费开源 |

## 2. 定位：语音陪伴智能体，卖点是千人千面

开头就说明白：这是一个语音陪伴的智能体，会陪聊、会回答百科。这部分不稀奇，市面上的陪伴类产品都有。

不一样的地方在于内容从哪来、长什么样：

| 维度 | 其他陪伴产品 | Open Anywhere |
| --- | --- | --- |
| 形态 | 专用设备，往往自带屏幕 | 一个低成本玩具 + 现场已有的屏幕 |
| 内容 | 厂商预置，靠内容库更新 | 现场生成，千人千面 |
| 场景 | 相对固定：陪聊、早教、故事 | 随现场变化：聚会、家庭、厨房、课堂、门店 |
| 扩展方式 | 增加内容与技能 | 增加场景，不增加内容 |
| 付费理由 | 买内容或买会员 | 买“让应用长出来”的能力 |

陪伴负责让人留下来，千人千面的应用负责让人愿意付钱。

## 3. 三层能力：对话、应用、角色

同一个智能体，由浅入深提供三层能力：

| 层 | 用户获得什么 | 例子 |
| --- | --- | --- |
| 对话层 | 聊天、百科、问答，纯语音即可 | 在客厅里随口问一句 |
| 应用层 | 为此刻现场生成的可运行应用，画面共享 | 聚会游戏、讨论看板、做饭计时板 |
| 角色层 | 智能体自己的形象出现在屏幕上，说话时会动 | 电视上出现它的脸，语气和动作跟着对话走 |

三层是递进关系：对话层是入口，应用层是付费核心，角色层建立情感连接。

## 4. 角色上屏：一个单独的应用 case

把智能体自己的形象放到电视上，聊天时它会有表情、会动——这是一个独立的应用案例，值得单独设计，而不是当作聊天的可选皮肤。

它成立的理由：

- **功能没变，性质变了。** 只有声音时它是助手，有了形象它就是角色。同一句话，由一个会看向你、会点头的形象说出来，感受完全不同。
- **屏幕的角色被反转。** 在此之前屏幕是输出设备，展示题目和比分；在这里屏幕是智能体的脸。
- **它直接对标陪伴机器人，但不卖硬件。** 竞品需要用户买一台机器放在桌上，我们直接用客厅已有的那块电视。
- **它最容易成为默认状态。** 没有应用在运行时，屏幕上放什么？放它自己——比空屏或等待提示更有价值。

需要验证的问题：形象是否让人更愿意持续对话；动作是否帮助理解还是构成干扰；不同观看距离下形象应该多大；它和应用画面如何共存或切换。

## 5. 收费模式

收费从硬件开始，但主要收入来自应用能力和运行能力。四条线：玩具、积分、运行、社区版。

### 5.1 小玩具：硬件收入，也是获客入口

- **语音入口不需要自带屏幕。** 屏幕来自现场那台电视，所以玩具本身可以做得非常便宜。
- **可以包装进任何一个萌物外壳。** 成本低，形态自由，用户买的不是一个设备，而是一个角色。
- **它是用户第一次接触产品的方式。** 硬件毛利之外，更重要的是把用户带进积分和运行体系。

当前实现用模拟硬件验证语音链路（见[现场语音入口](voice-entry.md)），玩具是这一入口的产品化形态。

### 5.2 百变积分：卖应用能力

这是最重要的一条收入线。积分对应的是“让应用长出来”这个动作，也就是产品最核心的价值。

| 项目 | 规则 |
| --- | --- |
| 创建新的 APP | 消耗 2 积分 |
| 在现有 APP 上修改 | 消耗 1 积分 |
| 包月会员 | 288 元/月，每天发放 20 积分 |
| 直接充值 | 1 元 = 1 积分 |

两点设计意图：

- **包月比充值便宜。** 288 元每月约 600 积分，折算单价明显低于直接充值的 1 元/积分，形成订阅激励。
- **修改比新建便宜。** 鼓励用户在已有应用上继续调整，而不是每次都重开一局；现场调整本来就是产品体验的一部分。

### 5.3 运行：云端时长或运行盒子

应用创建出来之后要运行，运行能力有三种获得方式：

| 方式 | 价格 | 说明 |
| --- | --- | --- |
| 会员包含的云端运行时长 | 包月会员每月自动获得 20 小时 | 适合多数家庭用户，时长够用即无需额外付费 |
| 云端按量 | 按时长计费 | 不订阅会员，或超出 20 小时后按实际使用付费 |
| 运行盒子 | 1000 元/个，一次买断 | 装在我们的固件上，本地运行，之后彻底不再收费 |

运行盒子把“用一次付一次”的心理负担换成一次性支出，适合经常使用、希望长期使用的家庭和商家。它会替代掉一部分云端运行时长收入，这是有意的取舍：用一次性收入换取渗透率和留存。

### 5.4 社区版：免费开源，换品牌

用户可以自己组建 Render 端，使用我们的固件，运行应用同样不收费。

- **对用户**：运行成本降到零，只要有一台自己的机器。
- **对我们**：开源扩散，把品牌打出去，把愿意省事的用户留在付费路径上。
- **边界**：社区版免的是运行端；应用创建仍然走百变积分，控制面仍由我们提供。

愿意折腾的用户免费，愿意省事的用户付费，两条路都留在生态里。

### 5.5 收入结构一览

| 收入项 | 收取方式 | 主要作用 |
| --- | --- | --- |
| 小玩具 | 一次性硬件 | 获客与硬件毛利 |
| 百变积分 | 288 元/月（每天 20 积分），或 1 元 = 1 积分充值 | 核心软件收入 |
| 云端运行时长 | 会员含 20 小时/月，超出按时长计费 | 持续收入 |
| 运行盒子 | 1000 元一次买断 | 高客单硬件，长期锁定 |
| 社区版 | 免费 | 品牌与生态 |

## 6. 客户分层

| 客户 | 典型选择 | 付费结构 |
| --- | --- | --- |
| 轻度个人 | 小玩具 + 按需充值 | 硬件 + 少量积分 |
| 家庭用户 | 小玩具 + 288 元包月 | 硬件 + 月费 |
| 高频家庭 | 小玩具 + 包月 + 运行盒子 | 硬件 + 月费 + 买断 |
| 商家（民宿、轰趴馆、门店） | 运行盒子 + 包月 | 硬件 + 买断 + 月费 |
| 技术用户 | 社区版自建 + 充值积分 | 积分 |

试点的优先级建议从商家开始：他们对一场活动是否值钱有直接判断，比个人用户的付费意愿更容易验证。

## 7. 计费口径与计量位置

| 计费对象 | 计量什么 | 计量位置 |
| --- | --- | --- |
| 百变积分 | 创建 2 积分 / 修改 1 积分 | 控制面（每次构建请求） |
| 云端运行时长 | 应用在 Render 上运行的小时数 | Render |
| 硬件 | 玩具、运行盒子 | 销售与激活 |
| 社区版 | 不计费 | 用户自建节点 |

积分发生在“应用被创造”这一步，控制面知道每一次创建和修改；运行时长发生在“应用正在跑”这一步，只有 Render 知道。两个计量点天然分离——这也是 Render 成为商业载体的根本原因。

## 8. 为什么是 Render 端

在整条链路里，Render 同时承担四个角色：

- **运行时长的计量点。** 每一路视频流、每一块在线屏幕都经过它。
- **运行盒子的载体。** 盒子就是固件 + Render，是最直接的商业化产品。
- **社区版的交付物。** 开源出去的那部分，正是让应用跑起来的那部分。
- **分发通道与数据回路。** 每块接入的屏幕都是入口，应用在什么现场被怎么使用，只有它看得见。

## 9. 验证路径

价格是假设，付费意愿需要按顺序验证，而不是先做完备的实现。

| 阶段 | 要验证的问题 | 交付形态 |
| --- | --- | --- |
| 演示 | 语音创建 + 应用上屏是否成立，千人千面是否被感知 | 自建 Render + 模拟硬件 |
| 早期用户 | 2 积分创建、1 积分修改是否被接受 | 云端 Render + 积分 |
| 订阅验证 | 288 元包月与每月 20 小时运行是否够用 | 云端 Render |
| 盒子验证 | 1000 元买断是否比持续付费更受欢迎 | 运行盒子 |
| 社区版 | 开源是否带来品牌扩散与实际转化 | 固件 + 用户自建 |

## 10. 本文不做的事

- 不论证 288 元、20 积分、20 小时、1000 元这些数字的合理性。它们是初始假设，需要用真实使用数据校准。
- 不定义积分、时长、授权与盒子激活的实现方案，这些属于后续技术设计。
- 不改变当前架构的非目标：当前版本仍是单租户、无计费的演示系统，商业能力的引入需要另立设计并修订架构文档。
