# Open Anywhere 产品设计

**说出你的需要，让应用在身边的屏幕上诞生。**

Open Anywhere 让人用自然语言描述此刻的需要，由 AI 创建可运行、可交互的应用，在身边的屏幕上呈现，并继续通过语音操作。用户从提出需求走到实际使用，无需接触代码、构建和部署。

朋友聚会是我们选择的第一个完整故事。产品面向的需求可以不断延伸：只要一个现场需要新的信息呈现或交互方式，就有机会创造一个适合当下的应用。

## 1. 产品愿景：需要发生在哪里，应用就出现在哪里

很多需要发生得很具体：今晚到场的三个人、孩子刚学的知识、一次临时会议、一家店今天的活动。现成应用往往要求人先寻找工具，再学习操作，最后把现场需要迁就到已有功能里。为这样的短暂需求单独开发应用，又通常不划算。

Open Anywhere 希望让“描述需要 → 创造工具 → 现场使用”成为普通人也能完成的连续体验。应用可以只服务一场聚会，也可以被保存、复用和继续修改。

在这个体验里：

- **语言表达意图**：用户说想做什么、和谁做、希望看到什么结果。
- **AI 创造交互**：把意图变成有界面、有状态、可以操作的应用。
- **屏幕承载现场**：把内容、进度和结果放在大家看得到的地方。
- **对话延续使用**：应用出现以后，用户还能开始、回答、查询、暂停和提出调整。

**场景可以不断生长，体验始终围绕“现场需要，现场创造，现场使用”。**

## 2. 用户是谁，为什么需要它

首批服务的用户，是身边有可用屏幕、希望组织一次互动或完成一个具体任务的人。他们熟悉自己的目的，却不一定会开发软件，也不愿为了一个临时需求研究复杂工具。

| 用户角色 | 当下要完成的事 | 现有负担 | 希望获得的结果 |
| --- | --- | --- | --- |
| 聚会发起者 | 让朋友一起玩起来 | 找游戏、解释规则、主持和记分 | 轻松开场，自己也能参与 |
| 家长或活动组织者 | 围绕某个主题组织互动 | 寻找合适内容、控制难度和节奏 | 符合参与者特点的活动 |
| 小团队主持人 | 组织一次讨论或共同决策 | 切换工具、手工整理、同步进度 | 所有人都看得懂、跟得上的共享界面 |
| 商家或场地方 | 给到场顾客提供活动体验 | 准备内容、安排主持、重复组织 | 可复用、可定制的现场服务 |

这些角色共享一个诉求：**“我知道此刻想做什么，请帮我把能用的东西准备好，并让我直接用起来。”**

## 3. 首个用户故事：朋友聚会，接下来玩什么？

### 3.1 故事

朋友聚会，最难的常常是那一句：“接下来玩什么？”

找游戏、讲规则、出题、记分，都需要有人组织。Open Anywhere 想让这件事变得简单：你只要说，“我们三个人，做个五题的电影知识竞赛，你来主持，放到电视上。”

AI 就围绕这次聚会创造游戏，邀请大家加入，通过语音互动，在大屏上呈现题目和比分。发起者也能成为玩家，大家一起抬头参与。

**有块屏幕，就能开场。**

### 3.2 体验从一句话开始，延续到一局结束

| 阶段 | 用户的动作或表达 | 产品应该提供的体验 | 用户获得的价值 |
| --- | --- | --- | --- |
| 发起 | “三个人，五题电影知识竞赛，你来主持，放到电视上。” | 理解人数、主题、题量与主持需求，确认目标屏幕 | 把组织活动的准备工作交给 AI |
| 准备 | 等待应用创建，必要时补充要求 | 简短回应，展示真实准备状态；失败时给出可执行的下一步 | 知道系统在做什么，避免不确定的等待 |
| 入场 | 玩家依次报名字、确认加入 | 大屏出现姓名卡片、就位状态与下一步提示 | 每个人都被邀请进入同一场活动 |
| 开始 | “开始吧。” | 说明简单规则，呈现题目并引导作答 | 减少学习和解释成本 |
| 参与 | 玩家依次回答，询问当前比分 | 明确回答人、判题结果和计分变化，语音与画面保持一致 | 能跟上进度，也能理解得分依据 |
| 调整 | “剩下的题换个主题。” | 在支持的范围内说明修改内容和生效时机，保留本局已有结果 | 玩法能回应现场兴趣 |
| 结束 | 看排名，说“再来一局” | 呈现结算与下一步选择，明确新一局会重置哪些内容 | 活动有完整收尾，也容易继续 |

首场演示以“创建 → 加入 → 开始 → 回答 → 计分 → 结算”为核心闭环。现场调整规则是后续增强点，需先验证进度保留和修改边界。

### 3.3 产品设计中值得保留的细节

**让每个人知道下一步怎么参与。** 准备完成、还缺谁就位、现在能否回答，都应该在屏幕上有明确提示。用户不需要猜一句系统才听得懂的口令。

**让组织者也成为玩家。** 主持、流程引导和计分交给系统，减少一个人一直忙于操作的情况。这是聚会场景里最直接的价值。

**让定制发生在用户看得见的地方。** 用户说出的“三个人”“电影”“五题”，应体现在玩家位置、题目内容与进度中。现场定制必须影响真实体验。

**让身份确认适合现场条件。** 首版可以通过姓名和明确确认关联玩家；声纹可作为后续增强。多人同时说话或身份不明确时，先引导依次回答和确认，保证结果归属清楚。

**让变化有规则。** 改主题、改分值应明确从哪一道题开始生效，历史得分不应被无提示地改变；新成员加入应交代如何计分。把真实聚会中的变化纳入设计，才能让用户放心继续玩。

## 4. 场景开放：从一个故事，长出更多应用

聚会验证的是一套通用能力：理解现场需要，创造一个应用，让人通过语言和屏幕完成互动。应用的内容、参与者和操作方式可以继续变化，下面只是探索示例。

| 现场 | 用户可能说的话 | 可以创造的应用 | 要验证的价值 |
| --- | --- | --- | --- |
| 朋友聚会 | “做个适合我们四个人的旅行主题小游戏。” | 主题问答、分组挑战、回合记分 | 更容易开场，更多人参与 |
| 家庭陪伴 | “用孩子今天学的动物知识，做一场亲子挑战。” | 图文问答、合作闯关、进度展示 | 内容贴合当下，家长和孩子能共同参与 |
| 学习与活动 | “把这几个知识点做成三组对战的练习。” | 分组练习、答题记录、结果回顾 | 降低准备成本，帮助发现理解差异 |
| 团队讨论 | “做个方案对比板，记录大家的意见和最后的选择。” | 方案卡片、意见记录、决策看板 | 减少记录与同步负担 |
| 门店活动 | “今晚有六桌客人，做一个电影主题互动活动。” | 活动大屏、轮次安排、排行榜 | 提供可定制的顾客体验 |
| 个人与日常工具 | “做一个分步做饭计时板，显示下一步该干什么。” | 多步骤计时器、清单、状态面板 | 把零散需求变成顺手的工具 |
| 智能体形象 | “把你自己放到电视上，聊天的时候动一动。” | 形象舞台、表情与动作、对话状态展示 | 让声音变成在场角色，屏幕成为智能体的脸 |

上表中“智能体形象”与前几行性质不同：前面几行是用户为某个任务指定的工具，这一行是智能体呈现自身。它不承载业务功能，承载的是在场感——只有声音时它是助手，有了形象它就是角色。这也为“服务已开启但还没有应用在运行”时的屏幕提供了内容：比起空屏或等待提示，一个会回应的形象更接近产品想表达的东西。形象的呈现方式、动作与切换规则需要单独验证，不能默认它与应用画面共存。

扩展场景优先满足三个条件：需求能清楚表达，主要交互能由轻量应用承担，使用结果能在现场直接看到。需要实时数据或外部服务的应用，还取决于相应数据和服务是否接入。

“场景开放”意味着用户不必只从预设玩法菜单中选择；每个新场景仍需验证可用性和实际价值。首期集中把一个故事做完整，再复用已验证的能力探索下一类需求。

## 5. 核心产品体验

### 5.1 从意图到使用的连续旅程

```text
说出需要 → 确认关键条件 → 准备应用 → 选择屏幕并打开
    → 引导参与 → 语音操作与画面反馈 → 调整或结束
```

系统优先确认会改变结果的关键条件，例如参与人数、目标屏幕和活动时长。能够合理默认的细节先给出默认方案，减少创建前的问答。

| 状态 | 用户应该看到什么 | 用户可以做什么 |
| --- | --- | --- |
| 等待需求 | 可用屏幕、需求示例 | 描述想做的事 |
| 准备应用 | 当前阶段、已用时间、明确的等待反馈 | 查询进度；在支持时取消或补充需求 |
| 就绪 | 应用名称、用途、参与说明 | 确认进入或开始 |
| 使用中 | 当前内容、参与者、进度与操作提示 | 操作、查询、暂停或提出修改 |
| 修改中 | 正在修改的内容、预计影响范围 | 知道当前应用是否仍可继续使用 |
| 结束 | 结果和后续选择 | 再来一次、切换应用或退出 |
| 失败 | 失败发生在哪里、如何恢复 | 重试、换屏幕或返回可用状态 |

这是面向用户的体验状态，不替代技术文档中的接口状态定义。

### 5.2 语音与屏幕各自发挥作用

语音适合表达意图、执行简单动作、查询和获取引导；屏幕适合呈现选项、结构、进度和结果。多人场景下，画面让所有人共享同一份信息。

界面应考虑远距离观看：主要文字清楚、当前状态突出、下一步明确。无需把开发日志和技术配置搬到用户面前。嘈杂场景先用轮流发言和明确确认降低误操作，后续再根据真实测试评估其他输入方式。

### 5.3 创造应用以后，还要持续可用

用户说“开始”“下一题”“查比分”时，系统直接操作正在运行的应用，及时给出结果。只有确实需要新功能或新界面时，才进入新的创建或修改过程。

对于修改请求，产品需要区分：

- **当前应用已支持的操作**：直接执行并反馈。
- **已有配置能够完成的调整**：确认影响后更新，例如尚未开始题目的分值。
- **需要重新构建的能力**：说明需要等待，并在支持时保留原应用和已有进度。

保留进度、跨重启恢复和热更新属于需要专门实现的能力；首期不将其作为默认保证。用户在退出、重启或重建前，应知道当前数据是否会保留。

## 6. 产品价值与差异

Open Anywhere 的价值需要由完整使用过程证明：用户提出需求后，是否真的更容易组织互动、完成任务，并愿意再次使用。

| 用户已有的选择 | 已有优势 | Open Anywhere 希望补足的体验 |
| --- | --- | --- |
| 现成游戏和工具 | 玩法成熟、启动稳定 | 贴合现场人数、主题和具体要求的定制 |
| 聊天助手 | 自然语言交流方便 | 持续可操作的界面、明确状态和共享结果 |
| AI 应用构建工具 | 能生成灵活的软件 | 从生成到现场打开、使用和语音操作的连续过程 |
| 人工主持与手工准备 | 灵活、有现场判断力 | 减少反复出题、流程引导和计分的准备负担 |

长期需要积累的，是需求到应用的交付成功率、适合语音操作的应用规范、现场交互设计，以及可复用的场景经验。生成能力、运行稳定性与用户体验共同决定产品价值。

## 7. 商业价值与验证路径

### 7.1 从真实使用出发

第一步在朋友聚会中验证：人们是否愿意等待并参与，定制是否带来明显差别，组织者是否更轻松，结束后是否愿意再来一次。

下一步优先接触有屏幕、持续接待多人活动的民宿和轰趴馆，验证他们是否愿意为定制内容与主持辅助付费。商家可以将互动活动作为服务套餐的一部分，客人获得围绕人数、主题和场合准备的娱乐体验。

这是首个商业切入方向。其他场景是否形成业务，取决于各自的使用频率、付费方、交付成本和需求验证。

### 7.2 可能的收费方式

| 阶段 | 付费方与收费假设 | 需要得到的证据 |
| --- | --- | --- |
| 单场试点 | 场地方按场次或活动套餐付费 | 活动被实际使用，商家愿意为下一场继续购买 |
| 稳定复用 | 商家按月或按额度订阅 | 使用频率稳定，支持成本可控，持续获得价值 |
| 后续探索 | 高频个人用户为更多创建、保存与定制能力付费 | 存在重复需求，并愿意为这些能力支付费用 |

价格由真实试用和成本数据决定。场次、订阅与个人付费是不同阶段的验证假设，不预设全部成立。

### 7.3 成本与规模化

单场收入需要覆盖应用生成与修改、运行、语音服务、设备部署和人工支持成本。常见需求可以在用户愿意的前提下保存和复用，减少重复等待与构建；新的需求仍可继续创造。

商业上应同时观察“这场活动有没有价值”和“交付这场活动花了多少成本”。商家重复使用、减少人工支持依赖之后，再评估扩大部署。

## 8. 首期范围与演进

| 阶段 | 产品重点 | 验证结果 |
| --- | --- | --- |
| 首个完整演示 | 三人、五题主题知识竞赛；语音创建，应用上屏，明确加入，依次回答，计分结算 | 用户能完成一局，提出的条件在游戏中真实生效 |
| 聚会体验完善 | 准备反馈、错误恢复、身份确认、适用范围内的规则调整与动态加入 | 真实聚会中的等待、晚到和误识别不会轻易打断活动 |
| 相邻场景探索 | 选择一种新玩法或新工具，继续复用创建、运行和控制流程 | 能力可以支持不同需求，且用户实际愿意使用 |
| 商业试点 | 在少量民宿或轰趴馆测试活动套餐 | 商家愿意重复付费，交付成本可控 |

首期聚焦真实语音输入、真实应用构建、可用画面与连续操作。声纹识别、多人同时抢答、任意屏幕自动连接、复杂玩法改造和跨重启保存等能力，按独立里程碑验证。

## 9. 如何判断产品有价值

首期关注：**用户能否完成一次体验，以及是否主动想再用一次。**

| 验证问题 | 建议记录的证据 |
| --- | --- |
| 开场是否更容易？ | 从提出需求到开始使用的时间，组织者需要介入的次数 |
| 应用是否符合现场需要？ | 人数、主题、题量等要求的满足情况，用户需要纠正什么 |
| 互动是否顺畅？ | 操作成功情况、反馈延迟、身份误归属、重试与中断原因 |
| 大家是否参与了？ | 各参与者的实际互动，一局完成情况，主动再来一局的行为 |
| 商家是否获得价值？ | 重复使用、实际付费或复购、活动准备与支持投入 |
| 能否持续交付？ | 构建与上屏成功情况、单场成本、人工支持时间 |

先记录真实测试的样本量、完成情况和原始反馈；指标基线形成后，再制定改进目标。

## 10. 对外表达

### 一句话定位

**Open Anywhere，让你说出需要，就能在身边的屏幕上创造并使用应用。**

### 聚会场景表达

**一句话，把客厅变成聚会现场。**

告诉 AI 人数、主题和玩法，让它准备游戏、邀请加入、引导互动并呈现比分。组织者也能成为玩家，大家一起抬头参与。

### 商业表达

我们从朋友聚会切入，下一步向民宿、轰趴馆验证付费需求，让一块已有的屏幕承载可以现场定制的互动娱乐。随着创建、运行和控制能力得到验证，再向更多现场需求扩展。

### 产品愿景表达

今天可以是一场电影知识竞赛，明天可以是一块讨论看板、一次亲子挑战，或一个此前没有想到的工具。用户说出需要，应用随之出现，并在现场发挥作用。
