# 产品扩展方向调研与建议

> 状态：Discussion（供产品讨论，不代表已排期）
> 版本：v0.1
> 日期：2026-10-25
> 关联：[产品设计](vision.md)、[系统架构](../architecture/overview.md)、[多应用并发与同会话更新](../architecture/interfaces/multi-app-sessions.md)、[用户管理端](../architecture/interfaces/portal.md)
> 说明：竞品信息来自公开产品页、新闻与评测（2025–2026），文末标注来源；未做逐一实测，具体能力以各产品当前版本为准。

## 1. 结论先行

- 我们卖的不是“AI 生成应用”，而是**从一句话到一个正在进行的现场**的完整交付：创造、上屏、参与、延续。扩展应该加深这条链路，而不是堆功能。
- 竞品已经证明三件事：**语音 + 大屏 + 聚会**成立；**扫码加入**是多人互动的事实标准；**AI 主持人**有明显情绪价值。我们目前最强的是“生成 + 上屏 + 语音”，最缺的是“参与层”和“运营层”。
- 最大的差异化空位仍然是：**固定玩法之外的当场生成**，以及把生成结果直接送到身边的屏幕上、用语音继续操作。这个空位不要丢。
- 近期最值得投入的五件事：**手机加入 v0、待机舞台、模板复用、屏幕画布契约、现场可靠性与声音**。它们共同改善“第一分钟”和“单场成本”。
- 中期最重要的战略升级：从“创建一个应用”走向**“编排一场活动”**（节目单、多应用、多屏、主持流程）。这是商家愿意持续付费的核心，而不只是生成一个游戏。
- 不建议做：通用聊天助手、以固定游戏库为主、早期做通用 SaaS 后端、早期做开放应用市场。它们会稀释“现场生成”的差异化。

## 2. 定位回顾：我们真正提供什么

### 2.1 三层价值

| 价值层 | 用户感知 | 我们已有的能力 | 同类产品通常缺什么 |
| --- | --- | --- | --- |
| 创造自由 | “我说什么，就能有什么” | 编码 Agent 按需生成任意 Web 应用 | 固定玩法、固定题库、固定模板 |
| 现场呈现 | “抬头就能一起看” | Render 运行、设备端 DLNA 投屏、共享大屏 | 个人屏幕、聊天窗口、单向标牌 |
| 连续操作 | “不用学，接着说就行” | 灵矽语音 + 应用管理 MCP + OpenAPI | 语音只做控制，不能创造和修改 |

### 2.2 护城河在哪里

生成质量本身会随着模型进步被拉平。真正会累积的是：

1. **交付链路**：从意图到构建、校验、启动、上屏、可用的成功率与耗时。
2. **现场数据**：什么应用被真正玩起来、在哪里卡住、如何被修改、是否再来一局。
3. **场景模板**：被验证过的玩法、话术、视觉与互动结构，可参数化复用。
4. **屏幕与设备网络**：越多屏幕接入，越多一次生成、多处复用的机会。

### 2.3 扩展判断标准

每个扩展方向先用五个问题过一遍：

1. 是否缩短“第一句话 → 第一次有效互动”的时间？
2. 是否让更多人参与，或让组织者更轻松？
3. 是否提升现场可靠性（不中断、不掉链子）？
4. 是否降低单场交付成本，或打开新的付费场景？
5. 是否强化“任意应用”的差异化，而不是退回固定内容库？

### 3.4 七个关键发现

1. **需求被验证，供给锁死在固定内容。** Volley、HEAT、Gig Game 都证明“语音 + 大屏 + 聚会”有人用，但玩法、题库、主持流程都是预先写死的。我们的“当场生成”是唯一能覆盖长尾现场需要的空位。
2. **手机加入是多人互动的事实标准。** Jackbox、Kahoot、Gig Game、Volley 都让玩家扫码或输房间码加入，手机承担输入、选择、绘画、抢答。纯语音在嘈杂、多人同时说话、需要精确输入时存在结构性短板。**语音应该做“发起与主持”，手机做“参与与输入”**，两者不是替代关系。
3. **AI 主持人的价值被低估。** Gig Game 把“AI 人格 + 实时解说 + 语音”当作核心卖点；Kahoot 的朗读只是无障碍，不是表演。现场的情绪价值来自语气、节奏、即兴反应和音效，而不只是把题念出来。
4. **商家要的是“活动运营”，不是“广告屏”。** AI 数字标牌已经能 prompt-to-app，但都是单向展示。商家真正需要的是可复用、可排期、可品牌化、能带来顾客停留和复购的活动；这正好是“语音互动 + 现场生成”的强项。
5. **AI 应用构建器的痛点是最后一公里。** 生成完还要部署、打开、登录、操作；等待时间与失败率普遍存在。我们的 Render + 设备端 DLNA + MCP 补上了“上屏 + 语音控制”，但必须把等待、失败恢复、预览做成产品能力。
6. **生成式 UI 正在标准化，大屏是空位。** MCP Apps / Apps SDK 让“工具带 UI”成为跨客户端标准，但目前主要发生在聊天窗口和个人设备。把同一套能力搬到大屏、加上多人语音与现场会话，是差异化机会。
7. **屏幕形态在扩散，但“值得打开”才是瓶颈。** 电视、机顶盒、闺蜜机、眼镜、随身屏都在增加；闺蜜机市场在 2025 年增长后于 2026 年回落，说明硬件不是问题，持续有价值的内容/体验才是。我们的“每次现场都能生成新东西”正好回应这一点。

### 3.5 三条可能的战略路径

| 路径 | 一句话 | 核心能力 | 变现方式 | 主要风险 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **A. 现场娱乐平台** | 朋友聚会与商家活动的“现场应用” | 任意玩法生成、手机加入、AI 主持、模板、商家后台 | 场次/订阅/品牌定制 | 低频、场地拓展成本、单场成本 | **主线**：先验证商家付费，再放大个人场景 |
| **B. 家庭与教育互动** | 亲子、课堂、培训的互动工具 | 内容注入、儿童模式、老师控制、结果回看 | 订阅/内容包/学校采购 | 获客、合规、内容安全 | 相邻扩展：复用 A 的参与与模板能力 |
| **C. 屏幕 Agent 平台** | 任何屏幕成为 Agent 的 I/O | 开放 MCP/API、应用市场、多租户、计费 | 平台分成/API 调用/设备授权 | 生态冷启动、标准竞争 | 长期：先自营闭环，再开放 |

三条路径不是互斥的，但资源有限。建议按 **A → B → C** 的顺序投入：A 验证“现场价值与付费”，B 复用 A 的能力扩大用户面，C 在契约、身份、计费、内容安全稳定后再开放。

## 4. 扩展方向

下面按现场链路分层。每条给出用户价值、对标依据与建议优先级（P0 = 下一个里程碑值得做；P1 = 之后 1–2 个里程碑；P2 = 验证后再投入）。

### 4.1 现场连续性：让屏幕“一直有用”

| 扩展 | 做什么 | 用户价值 | 依据 | 优先级 |
| --- | --- | --- | --- | --- |
| **待机舞台** | 无应用时显示可用屏幕、对话状态、示例、二维码、品牌待机页；从待机到应用平滑切换 | 不再空屏等待；商家可常驻展示 | #50、#64、#48；Alexa+ 的个性化待机屏、AI 标牌的常驻展示 | P0 |
| **预热与秒开** | 预构建常用场景模板、预热 Node/Chromium、进程池；构建阶段在大屏上真实呈现进度 | 缩短“第一句话 → 第一次有效互动”；减少聚会冷场 | AI 构建器的共同痛点是等待；#13 | P0 |
| **转场与声音** | 应用切换、开始、结算的转场动画与音效；BGM、音量、淡入淡出、打断 | 现场“像一个节目”，而不是打开一个网页 | Jackbox、Gig Game 的节目化包装；#8 | P0 |
| **断线恢复** | 应用崩溃、投屏中断、网络抖动后的自动恢复；恢复本局状态 | 付费场地最怕“掉链子” | 商业场地的可靠性要求 | P0 |
| **精彩回放 / 分享** | 自动截图或录屏、比分海报、二维码分享、精彩瞬间 | 活动有收尾、可传播、可复用 | Gig Game 的社交分享与打印卡片 | P1 |

### 4.2 参与方式：让每个人都进来

| 扩展 | 做什么 | 用户价值 | 依据 | 优先级 |
| --- | --- | --- | --- | --- |
| **手机加入 v0** | 大屏显示二维码/房间码；手机浏览器加入，承担身份确认、答题、投票、抢答；与语音并存 | 解决嘈杂环境、精确输入、无声玩法；扩大可玩的应用类型 | Jackbox、Kahoot、Gig Game、Volley 的事实标准 | P0 |
| **身份与声纹** | 声纹注册/识别、玩家自动归属、抢答仲裁；不确定时回退到确认 | 免手操作、更“神奇”；减少误归属 | #16、#14；产品设计已把声纹列为后续里程碑 | P1 |
| **轮流 / 抢答 / 组队** | 平台化的回合管理、抢答器、队伍分配、计分规则 | 应用不必每次重写多人规则；生成质量更稳定 | Jackbox 的回合制、Kahoot 的排行榜 | P1 |
| **观众模式** | 旁观者投票、弹幕、表情、送花；不占玩家位 | 大场面也能参与；商家活动更有氛围 | Jackbox 上万人观众、Slido/Mentimeter 的 Q&A | P1 |
| **多语言字幕** | 屏幕字幕 + 手机端翻译；语音与画面语言可不同 | 民宿、国际化的真实需求 | Kahoot 70 种语言、Gig Game 多语言玩家 | P2 |
| **儿童 / 家庭模式** | 内容审核、时长控制、护眼提示、家庭友好过滤 | 打开亲子场景；降低内容风险 | Jackbox 家庭友好模式与脏话过滤 | P1 |

### 4.3 创作与修改：让“说一句”真的够

| 扩展 | 做什么 | 用户价值 | 依据 | 优先级 |
| --- | --- | --- | --- | --- |
| **现场迭代** | 已实现的 `update-app`：同一 AgentAPI 会话内修改；补上“保留本局进度”的方案与话术 | 现场改主题、改规则不打断活动 | #68、#69、[多应用并发与同会话更新](../architecture/interfaces/multi-app-sessions.md) | P0（已实现，补状态保留） |
| **模板 / 场景库 v0** | 把成功应用保存为参数化模板（人数、主题、品牌、题库、时长）；下次一句话复用 | 降低等待与成本；商家可重复使用；质量下限更稳 | Jackbox 的内容包、Gig Game 的节目模板、AI 标牌的品牌模板 | P0 |
| **内容注入** | 上传/拍摄题目、菜单、课本、照片、链接；构建时引用 | 定制更真实；教育和商家场景必需 | Kahoot 从文档/PDF/视频生成；Gig Game 从 URL 生成题目 | P1 |
| **预览与确认** | 先在手机或小窗预览，确认后再上大屏；支持“换一个版本” | 避免半成品上大屏；给组织者掌控感 | AI 构建器的 preview；现场体验的基本护栏 | P1 |
| **主持人人格库** | 可选角色、语气、方言、音色；支持品牌专属主持人 | 情绪价值；不同场景的调性 | Gig Game 的 AI 主持人格；灵矽 TTS 能力 | P1 |
| **主动主持** | AI 不只响应，还能推进流程：计时、提示、救场、串场、结算 | 组织者真正能当玩家 | 产品设计 3.3“让组织者也成为玩家” | P1 |
| **语音指代** | 用户说“把这个放大”“看左边那个”，屏幕高亮/聚焦对应元素 | 语音与画面协同，降低“说不清”的成本 | 尚无同类产品做好；可作为差异化交互 | P2 |
| **现场记忆** | 记住本场玩家、比分、偏好、上一位冠军；跨应用延续 | “再来一局”“刚才那个冠军”更自然 | 产品设计 3.2 的连续体验 | P1 |

### 4.4 屏幕与部署：让屏幕无处不在

| 扩展 | 做什么 | 用户价值 | 依据 | 优先级 |
| --- | --- | --- | --- | --- |
| **画布契约** | 应用声明目标画布、安全区、横竖屏、是否支持音频；Render 按屏幕能力适配；构建时按目标比例自检 | 解决投屏显示不全、布局错位 | #71；电视与手机/平板的差异 | P0 |

## 6. 优先级与路线图

### 6.1 P0：下一个里程碑

1. **手机加入 v0**
   - 范围：大屏展示二维码/房间码；手机浏览器加入；身份确认、答题、投票、抢答；应用状态在大屏与手机间同步。
   - 为什么先做：它同时解决“嘈杂环境听不清”“多人同时说话”“精确输入”“无声玩法”四个问题，是参与层的地基。
   - 验收：从扫码到加入 < 15 秒；手机操作与大屏状态一致；语音与手机可混用；不加入手机也能完成纯语音流程。

2. **待机舞台 + 预热**
   - 范围：无应用时显示对话状态、可用屏幕、示例、二维码；构建进度上屏；常用模板预构建；Node/Chromium 预热。
   - 为什么先做：空屏和等待是“第一分钟”最大的流失点；商家也需要常驻展示。
   - 验收：需求 → 首次画面 P50 < 20 秒（模板场景）；空屏时长显著下降；构建失败有可执行提示。

3. **模板 / 场景库 v0**
   - 范围：成功应用保存为模板；参数化（人数、主题、品牌、题库、时长）；一句话实例化；模板来源可私有可共享。
   - 为什么先做：直接降低构建成本与等待，是商家复用的前提，也是质量下限的保障。
   - 验收：模板复用率、模板场景的上屏时间、单场构建成本。

4. **屏幕画布契约**
   - 范围：应用声明目标画布、安全区、横竖屏、音频能力；Render 按屏幕适配；构建自检覆盖目标比例。
   - 为什么先做：显示不全是投屏体验的硬伤，也会让“定制”显得不可靠。
   - 验收：不同屏幕/比例下的布局问题率；构建产物一次通过率。

5. **现场可靠性与声音**
   - 范围：上屏成功率、崩溃恢复、投屏/网络中断恢复、关键路径可观测；基础音效、BGM、转场、音量控制。
   - 为什么先做：付费场地最怕现场事故；声音是最低成本的情绪价值。
   - 验收：上屏成功率、平均恢复时间、现场主观评分。

6. **现场迭代的状态保留**
   - 范围：在已有 `update-app` 设计上，补“修改时保留比分/进度”的方案；明确哪些修改需要重启、哪些可以热更新；给用户清楚的话术。
   - 为什么先做：现场调整是真实需求，但“改一下就把这局弄没了”会直接摧毁信任。
   - 验收：修改成功率、进度保留率、修改后的继续使用率。

### 6.2 P1：之后 1–2 个里程碑

- **活动编排 / 节目单**：多应用 + 转场 + 主持流程，把“应用”升级为“活动”。战略优先级高于单个玩法。
- **多应用 / 多屏**：主游戏 + 记分 + 计时 + 照片墙；画中画/分屏。
- **商家后台 v0 + 品牌包**：模板、历史、基础数据、品牌定制。
- **内容注入**：文档/图片/链接/题库，让定制贴近真实内容。
- **预览与确认**：手机预览、版本选择、确认上屏。
- **主持人人格与主动主持**：人格、音色、方言、即兴解说、计时与串场。
- **观众模式**：投票、弹幕、表情、送花。
- **儿童/家庭模式**：审核、时长、护眼、家庭友好。
- **投屏协议扩展 + Render 盒子**：AirPlay/Chromecast/盒子，覆盖商业部署。
- **精彩回放 / 分享**：比分海报、精彩瞬间、二维码。
- **数据飞轮**：构建与运行数据回流模板和提示词。

### 6.3 P2：验证后再投入

- 声纹身份与抢答仲裁（准确率、隐私、成本都需要验证）。
- 应用/场景市场与创作者分成。
- 开放 MCP/API 给第三方硬件与屏幕。
- 数字人形象主持、环境感知（人数/情绪/光线）。
- 离线/弱网模式、多语言/出海、跨场次会员与积分。
- 云端多租户 Render 与弹性调度。

### 6.4 不建议做

| 方向 | 为什么不 |
| --- | --- |
| 通用聊天助手 | 会把产品拉回“聊天窗口”，丢失大屏与现场的差异化 |
| 以固定游戏库为主 | 与“任意应用生成”冲突；固定库可以作为模板，但不能成为主形态 |
| 早期做通用 SaaS 后端（登录、支付、数据库、CMS） | 需求未验证，成本高，且会把现场体验拖慢 |
| 早期托管任意第三方应用 | 安全、合规、成本都不可控；先做受约束的应用包 |
| 早期追求全协议、全设备 | 先用主流电视 + 盒子 + 浏览器覆盖大多数现场 |
| 自建 ASR/TTS/大模型 | 灵矽已经提供；我们的价值在链路与体验，不在模型 |

## 7. 验证指标

### 7.1 北极星

**从第一句话到第一次有效互动的时长**，以及**一场活动中所有人真正参与的有效互动分钟数**。前者衡量交付效率，后者衡量现场价值。

### 7.2 体验指标

| 指标 | 说明 | 目标方向 |
| --- | --- | --- |
| 首次上屏时间 | 需求提出 → 大屏出现可用画面 | 越短越好；模板场景应显著快于全新生成 |
| 上屏成功率 | 构建成功且投屏进入播放状态的比例 | 付费场景要求接近稳定 |
| 参与率 | 在场人数中实际加入/回答的比例 | 越高越好 |
| 组织者介入次数 | 一场活动中需要人手动救场/解释的次数 | 越低越好 |
| 语音误识别/误归属率 | 识别错、归错人、抢答冲突 | 越低越好 |
| 再来一局率 | 结束后主动继续的比例 | 核心留存信号 |
| 单场成本 | 构建、运行、语音、支持的总成本 | 越低越好 |

### 7.3 商业指标

- 场地方复购率、周活跃场次、活动套餐收入。
- 模板复用率、单场人工支持工时。
- 商家愿意为哪些能力付费：品牌定制、排期、数据、可靠投屏、主持辅助。

## 8. 开放问题

1. **主入口是语音还是手机？**
   建议：语音负责发起、主持、查询与调整；手机负责加入、精确输入、选择与投票。两者是双通道，不互相替代。

2. **应用形态是每次全新生成，还是模板优先？**
   建议：模板优先、生成兜底。高频场景用模板保证速度与质量，长尾需求继续生成。这样既保留差异化，又能控制成本。

3. **屏幕归谁？**
   建议：双轨。个人场景用用户已有电视/投影；商业试点提供 Render 盒子，保证可靠性与运维。

4. **先做家庭/教育，还是先做商家？**
   建议：商家先验证付费（民宿/轰趴馆），家庭做口碑与传播。两条线的核心能力（模板、手机加入、儿童模式、可靠投屏）高度复用。

5. **生态开放到什么程度？**
   建议：先把自营闭环做稳，再开放 MCP/API。开放的前提是应用包契约、身份、计费、内容安全都稳定。

6. **生成内容的安全边界谁负责？**
   需要提前定义：平台审核、商家审核、用户自担的边界；儿童场景要更严格。这是商业化前必须回答的问题。
